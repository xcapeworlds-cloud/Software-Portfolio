01 / Featured technical case study · Unity / C#

Sugar.io — separating gameplay responsibilities

A tornado arena prototype with movement, AI opponents, collectible objects, growth, and collision rules.

The problem: As movement, AI opponents, collectible interactions, growth, and collisions were added, gameplay logic became harder to reason about. I focused on separating behaviors into scripts with clearer responsibilities instead of coupling every feature into one system.

My role: Gameplay direction, project structure, reviewing and organizing implementation. I used AI assistance for parts of the code and worked to understand and improve the results. The showcase changes are not claimed to be compiled or play tested in the original Unity project.

What I learned: I learned to treat the prototype as a way to validate core gameplay mechanics before locking in the system architecture. Starting with a minimal playable implementation helped me identify which behaviors needed separate responsibilities, where components interacted, and what was worth refactoring once the requirements became clearer.

Technical approach: The C# showcase separates player control, AI behavior, collectible interactions, and game state into focused components. Architecture notes describe component responsibilities and tradeoffs, making the code easier to inspect and extend.

Verification: Source and documentation are public. Changes made for the code showcase were not compiled or play tested in the original Unity project.
